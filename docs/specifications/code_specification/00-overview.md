# 00 系统范围与原则

## 产品是什么

售卖 **6 个 API 产品** 的企业服务平台。6 个产品均提供 API 对接，按调用次数收费；其中 **3 个产品** 额外提供 WebUI（同步提交、同步展示结果）。

系统分三个界面，对应已认可的三套视觉场景：

| 界面 | 使用者 | 视觉 |
|------|--------|------|
| 登录前门户 | 未登录访客 | `portal.css`，类前缀 `p-` |
| 客户平台 | 已开通的企业用户 | `admin.css` + `theme-customer` |
| 运营后台 | 内部运营人员 | `admin.css` + `theme-ops` |

## 完整闭环（必须能独立跑通）

1. 线下签约、合同生效（系统外）。
2. 运营在后台创建企业租户、发放登录账号，开通产品并录入额度/单价。
3. 客户用账号登录客户平台：查看文档、管理 API Key、调用产品；3 个产品可用 WebUI 同步提交并看到结果。
4. 每次成功调用按约定扣次数，写入流水与账本；额度不足或未开通则拒绝。
5. 续费、加额度、调账仍由运营按合同在后台操作。

## 明确不做（首期）

- 门户自助注册、在线签约、购物车、支付网关
- 客户自助开通产品或自助加额度
- 产品执行异步化（任务队列、提交后再查询）
- 微服务拆分、独立计费服务、消息总线（Kafka 等）

若某产品日后变为长耗时任务，仅对该产品升级执行模型，不作为默认架构。

## 设计原则

1. **计费可对账**：余额/剩余次数不能单独改；必须有账本分录。
2. **开通可审计**：租户、产品授权、额度、Key 的变更记录操作者。
3. **一条执行路径**：WebUI 与开放 API 走同一 `Fulfillment`，避免两套计费逻辑。
4. **视觉规范只消费**：新 UI 必须落在已有 CSS 类名与 Design Tokens 上。
5. **YAGNI**：模块边界先划清，部署保持单体，直到有明确拆分理由。
